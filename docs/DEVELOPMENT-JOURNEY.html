1. The brief — "show me what this repo can do, as something a beginner can build"

3. Design decisions

  • Project shape: a tiered "Prompt-to-Reel". One Mixamo character performs 4 prompted moves, each rendered side by side with its AI source clip.
    • Tier 0: browser only, Node + fal key, no GPU.
    • Tier 1: GVHMR HQ pass on the local GPU, plus optional WiLoR/MANO fingers.
    • Tier 2: Blender side-by-side render and an ffmpeg concat.
    • Tier 3: numbers instead of eyeballing (jerk, foot-skate, hips wobble, limb stretch).
    • Why tiers: the HQ path needs a CUDA GPU, about 5 GB of checkpoints, and two academic-license registrations (SMPL-X, MANO). A single all-or-nothing project would stall at minute 10 for most beginners. Each tier produces something.
    • Rejected (inferred from the guide, not stated as rejected): a pure HQ demo (too much setup), and a browser-only demo (shows nothing of the repo's main contribution, GVHMR).
  • Wrapper next to the repo, not edits inside it. prompt2rig_reel/ sits beside prompt2rig-main/ and changes no repo files. Repo updates stay clean, and the user's question "do these reel demos come with the repo?" had a crisp answer: no.
  • Git Bash first, after the user asked about it. The guide had been written for PowerShell. The wrapper switched to bash: make_env.sh writes UTF-8, and setup_hq.sh shells out to powershell.exe -ExecutionPolicy Bypass only for the repo's setup.ps1.
  • Never handle the fal key. make_env.sh uses read -rsp. The RC session was told never to print or transmit the key, and the key prompt was opened in a visible Git Bash window for the user to paste into. This cost a human round-trip (section 6, #5) but was non-negotiable.
  • Default prompts follow the repo's own rule ("face the camera, limbs clear of the torso, no spins, flips, floor work or crossed arms"): tennis forehand/backhand, Macarena, orchestra conductor, counting on fingers. The last one doubles as a finger-tracking test.
  • Defaults instead of blocking on answers. The thread asked the user 5 questions (GPU, Blender version, prompts, character, fal credit) and built with defaults in the meantime. Michelle was the default rig and Blender 4.5 the default path.
  • Descoped / YAGNI: no edits to hq/setup.ps1 (its failures are wrapped and verified from bash instead of patched in place), no CPU/AMD fallback for the worker (it hard-codes CUDA), and no automation of the browser UI (the user presses generate and ↓ glb by hand).

4. The core problem: Windows is not where this repo was born — and neither were we

The repo was "Tested on Windows 11 with an RTX 4090" (README, line 188). It works on Windows, but its instructions assume PowerShell, a big GPU and a clean path. The real crux was ten small frictions that each fail silently. They were found by reading the code, not by hitting them:

  1. server.mjs parses .env as UTF-8 with a line regex. PowerShell 5.1's echo FAL_KEY=x > .env writes UTF-16LE, the regex never matches, and you get FAL_KEY is not set.
  2. The parser does not strip quotes, so FAL_KEY="abc" sends the quotes and fal returns 401. make_env.sh strips them and doctor.sh flags them.
  3. hq\setup.ps1 is blocked by execution policy, and the zip carries Mark-of-the-Web.
  4. $ErrorActionPreference = "Stop" does not stop on failing native exes in PS 5.1, so a failed uv pip install carries on. setup_hq.sh therefore ends with an explicit import torch, gvhmr, ultralytics, fastapi; assert torch.cuda.is_available().
  5. torch 2.7.1 from cu126 lacks sm_120 (RTX 50). CUDA_INDEX in config.sh sed-patches a copy to cu128.
  6. MAX_PATH under Downloads\...\mixamorig_stefan\prompt2rig-main. doctor.sh reads LongPathsEnabled.
  7. The worker itself shells out to ffmpeg, so ffmpeg must be on PATH for Tier 1, not just for renders.
  8. Hard-coded paths: README says Blender 5.2, and tools/capture.mjs assumes Chrome's default path.
  9. The worker is CUDA-only (device=0, half=True).
  10. Both servers bind to localhost only, so Defender prompts can be denied safely.

And a Git Bash layer on top:

  • backslash paths break, so use hq/.venv/Scripts/python
  • don't source activate; call the venv's Python by path
  • mintty may not forward Ctrl+C to native Windows processes, so run.sh traps and runs taskkill //F //T //PID on the worker's winpid
  • // doubling for Windows-style flags

The wart in this section: friction #2 in the published guide is wrong for the user's actual copy. The guide says ".env.example is absent in your copy, so the README's cp .env.example .env fails." On the laptop, prompt2rig-main\.env.example exists (67 bytes, 20:51) and so does .gitignore. The cloud project-files copy dropped every dotfile in the upload, and the build session read only that copy. The 21:24 hand-off ("Your copy has no .env.example") repeated it. Nobody noticed until this session listed the laptop folder. It caused no harm, because make_env.sh writes .env directly, but the guide states something false.

  • Rule learned: a mirrored copy is evidence about the mirror. Check claims of "file X is missing" against the real disk.

Agents and AI machinery: no subagents and no workflows. Everything was done inline by the coordinator, the build thread, and three short RC sessions (one in the build thread, two in this one). Model identity is not recorded here on purpose.

Tech stack, as built:

  • prompt2rig = Node server.mjs (port 5177, fal proxy) → browser three.js app (public/app.js, retarget.js, stage.js)
    • MediaPipe Pose (pose: heavy) gives a live per-frame retarget onto a Mixamo rig. X Bot, Michelle and Soldier come from jsDelivr three.js@r169/examples/models/gltf/.
    • Optional Python HQ worker (hq/worker.py, FastAPI): GVHMR + SMPL-X, plus WiLoR/MANO for fingers.
  • Video: fal image-to-video (H3 Max Turbo / FLUX 3 Max) from a one-time FLUX.1 schnell "performer" image (PERFORMER_PROMPT in public/app.js). The performer URL is cached in browser localStorage.
  • Wrapper: bash + config.sh. metrics.py needs only numpy: it reads GLB animation channels directly and computes jerk from quaternion log differences.

6. What went wrong, and the fixes

  1. Wrong device folder connected at start (other-project). Fix: the coordinator retracted the write instruction within 41 s. Folder access to mixamorig_stefan was requested at 21:03.
  2. "Already there" claim that wasn't (21:02, coordinator). The guide was in cloud project files only. Fix: device_commit_files to the laptop at 21:04. Cost: three frustrated user messages.
  3. Guide friction #2 false for the real disk (see section 4). Not fixed in the guide yet.
  4. Two contradictory instructions two minutes apart (21:24 "run ./make_env.sh yourself"; 21:26 "Easier now: there's a Git Bash window titled "prompt2rig" open… Paste your key there"). The second superseded the first, but the user received both.
  5. The key window died before the user used it. The user typed "done" at 21:59, 33 min after the window opened. .env was written at 21:58 (78 bytes), but the app was not up: "the first window had stopped". The cause was never established. A guess I can't verify: the window ran make_env.sh && run.sh --live, and the server process exited, or the window was closed. Fix: RC restarted the app in a new Git Bash window "prompt2rig app" and confirmed it up at 22:01.
  6. Ambiguous question answered twice. "where does the human character come from?" got a two-part answer (performer image + Mixamo rig). The user meant only "the human character on the left". The coordinator answered that directly at 22:09.
  7. This session: "%USERPROFILE%\.claude\ is off-limits." That was too strong. Fix: RC session, after the user's correction.
  8. This session: RC started in the wrong folder (the other-project environment) despite folder: mixamorig_stefan. The user caught it and I stopped it. The second attempt landed in a new environment (mixamorig_stefan), verified with list_devices.

Near-misses:

  • The 21:01 instruction to save the guide into other-project would have put project files in an unrelated folder. It was retracted before anything was written.
  • config.sh still points at Blender 4.5. The laptop has 4.4. The 21:24 message offered "I'll point config.sh at the 4.4 folder unless you'd rather install 4.5". It never got a reply and was never applied. doctor.sh will report Blender as missing, and render_reel.sh exits with Blender not found: edit BLENDER in config.sh.

Fragility and luck:

  • The first RC session ran with cwd in the other-project folder and still worked, because every command used absolute paths. It was lucky, not designed.
  • Asset loads depend on the jsDelivr CDN. A blocked CDN leaves the rig/pose pills on "loading".
  • The VRAM figure ("likely 4 GB") for the RTX 3050 Laptop GPU is a guess from the model name. It was never measured with nvidia-smi --query-gpu=memory.total.

7. Verification

Checked by observed effect:

  • App up: RC reported HTTP 200 on http://localhost:5177 and the pills x bot and pose: heavy green, hq · worker offline, no console errors (22:01, from the RC session's report).
  • .env: plain text, unquoted FAL_KEY (RC report). I confirmed it exists on disk at 78 bytes, mtime 21:58, without reading its contents.
  • metrics.py: run in the cloud container on two synthetic GLBs (smooth vs noisy). The jerk matched the analytic value within 3% (build-thread report; not re-run by me).
  • The demo itself, verified by me from the recordings:
    • Live mode (live · mediapipe), portrait 9:16, h3 max turbo · fastest, source performer → video.
    • Seven takes, all from the app's built-in preset list, not from prompts.txt:
      • #1 and #2 "throws boxing jabs and hooks toward the camera"
      • #3 "celebrates a victory, jumping and pumping both fists in the air"
      • #4 "does a karate kata with straight punches and front kicks"
      • #5 "shoots an imaginary basketball jump shot"
      • #6 "does jumping jacks"
      • #7 "does an energetic hip hop dance with wide, open arm movements"
    • Generation times shown on the take cards: 1.8 s, 1.8 s, 2.1 s, 2.0 s and 3.6 s (#2 through #6).
    • The rig used was X Bot, not the Michelle default.

Observed but unexplained:

  • Take #4 (karate kata) shows no live badge, and its ↓ glb button looks greyed out in both recordings. Possible cause: pose tracking produced no usable motion for that clip (it has kicks, and side-on limbs break the repo's own prompt rule). Not investigated.
  • In take #5 the video model gave the performer a real basketball for an "imaginary" jump shot. The prompt adjective was ignored. This is a nice visible example of video-model prompt drift.

Not verified:

  • No GLB was exported: prompt2rig-main\takes\ does not exist.
  • Tier 1 (setup_hq.sh), Tier 2 (render_reel.sh) and Tier 3 on real takes have never run on the laptop.
  • npm install was never run (no node_modules). Tier 0 does not need it; only tools/capture.mjs does, via puppeteer-core.
  • The fal cost figures (≈$0.016/s for H3 Max Turbo, ≈$0.021/s for FLUX 3 Max, ≈$0.08 per 5 s clip) were quoted by the build thread as list prices and not checked against the fal billing page. At that rate the 7 takes plus one performer image come to roughly $0.56–0.60, an estimate only.
